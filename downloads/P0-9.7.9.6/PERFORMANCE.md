# P0-9.7.9.6 普通应用唤醒交接记录

## 改动与证据

基线为 0.6.18-dev / 33 和 naozho_wake 1.3.1 / 5。旧观察器已经订阅默认显示器的状态变化。限制来自正式 RETURN 前复用的 DailyBoard.allowPage()，它接受特定前台页面，并要求给其他应用逐项登记。桌面小部件另有一条预呈现支路。仅移除小部件无法开放普通应用返回。

候选为 0.6.19-dev / 34 和 naozho_wake 1.4.0 / 6。日常电源键模块继续使用原有页面检查。唤醒模块核对当前用户、显示器、焦点窗口、ActivityRecord、任务号及 Activity 的真实 UID，两次检查间来源必须稳定。清晰可识别的普通浏览器、文件管理器、游戏及其他 Activity 走同一路径，无需登记包名。真实通话、系统认证、权限浮层、未知遮挡和无法区分安全页面的通用设置容器仍可能被拒绝。应用自行在普通非安全窗口内绘制的内容无法仅凭窗口元数据识别。开发退出沿用现有模式逻辑。时钟在自己的任务中启动，原任务留在后台；Android 仍可因内存压力回收应用进程。自动返回不需要小部件，也不要求先打开时钟。

### 黑色过渡与权限

KernelSU 进程在真实 OFF 进行准备，允许在 ON 边沿做一次补救。系统必须能确认普通窗口身份。用户通过系统设置授权的独立无障碍服务使用 Android 14 起提供的按窗口附加 SurfaceControl 接口。源窗口仍由原应用拥有。服务只用窗口元数据，黑色视图消费触摸，电源按键和系统导航仍由系统处理。接收器继续要求 STATUS_BAR_SERVICE；增加窗口限定请求时核对开机号、息屏代、前台任务和应用私有授权。正式唤醒路径独立执行完整 FULL_WAKE、权限、投递证明及双阶段协议。

黑色视图覆盖被核验的源窗口。全屏应用、带系统栏的普通应用、分屏及系统顶层窗口具有不同的显示边界。候选保留系统栏、紧急界面及系统弹窗在上层。应用窗口附加成功、Surface 提交、显示器开始发光、原应用是否闪现、实际触摸是否被挡住是五类不同证据。原应用不可见时，附着于它的层也可能随 Android 窗口切换离开屏幕；模块只能确认程序发出的撤销时点。黑幕授权不可用时仍尝试正式返回，需在现场将遮罩缺失单独记下。

离线核对同机固件的 framework/services DEX，输入路径为 ViewRootImpl.setView → WindowManagerService.addWindow → WindowState.openInputChannel。系统为嵌入视图另行 grantInputChannel，updateInputChannel 根据子窗口的 flags 和裁剪范围设置输入区域。AccessibilityInteractionController 将已创建的 Surface 附到源应用窗口。输入宿主本身不可见、不可触摸、不可获焦。公开的 attachAccessibilityOverlayToWindow 没有宿主已显示的返回值；本机的 SurfaceFlinger 与 InputDispatcher 是否实际显示并消费触摸须独立验证。

### 正式完成条件

时钟只为同一 request_id、wake_epoch_id、sender 等字段完全匹配的请求写回执，时机在本次硬件首帧已提交、MainActivity 确认焦点及 LOCKED + 80 且仅有时钟包以后。模块独立核验 RETURN 与 COMMIT 各一次、系统实际焦点和锁定状态。黑幕有独立撤销、异常清理和停用路径。窗口未知、出处变化、维护暂停或保护界面出现时优先恢复原系统界面。任何单条黑色图层或小部件日志都不足以宣布接管成功。
